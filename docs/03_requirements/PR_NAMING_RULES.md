# PR 命名規則

版本：1。需求來源：使用者明確要求所有後續 PR 使用中文名稱、單一類型前綴，並將規則寫入 repo 供 AI 工作台遵循。

## 適用範圍與規則來源

本規則適用於本 repo 的 Agent，以及 AI 工作台為受管理專案建立的 PR。它是 PR 標題的 canonical requirement，供 PRD、SRS、SDD、Feature Spec 與跨 Agent 操作指引引用。需求 ID 為 `WB-016`，驗收 ID 為 `AC-WB-016`。

工作台與 Agent 應先讀取 repository 的已確認規則，再依變更內容產生標題。目標專案有其他已核准規則時，依既有 Authority 處理；發現衝突須指出並取得確認，不能自行覆蓋或退回英文預設值。專案內容與模型回覆不是新增命名權威。

## 標題格式

`type: 正體中文摘要`

- 每個標題只放一個小寫類型前綴，後接半形冒號與一個空白。
- 摘要用正體中文說明實際變更；專案名稱、產品名稱、API 等必要專有名詞可保留原文。
- 不加粗、不包方括號，不疊加 WIP、Draft、PASS、QA 等狀態名稱；草稿狀態使用 GitHub 的 Draft 功能。
- 主要使用 `feature`、`fix`、`bug`；只有內容明確適合時才使用 `docs` 或 `refactor`，不自行擴增大量前綴。

| 前綴 | 用途 |
|---|---|
| `feature` | 新增使用者功能或能力 |
| `fix` | 修正既有行為或錯誤 |
| `bug` | 針對明確功能缺陷的修復；與 `fix` 擇一 |
| `docs` | 純文件、專案計畫或專案紀錄更新 |
| `refactor` | 整理內部實作，不改變既有對外行為 |

範例：

- `feature: 新增 AI 專案工作台與首次使用流程`
- `fix: 修正取消後 FREE 方案仍顯示舊價格與異常狀態`
- `bug: 修正切換專案後誤送上一個專案的內容`
- `docs: 更新專案計畫與對話紀錄`
- `refactor: 整理專案同步流程`

## AI 工作台的要求

1. PR 建立流程必須依本文件及目前專案已核准規範決定類型與中文摘要，不得以固定英文 `Workbench project records` 作為預設標題。
2. 現有工作台僅同步已確認的專案紀錄檔時，應使用 `docs`；例如 `docs: 更新「小店庫存管理」的專案紀錄`。是否包含聊天仍由原有預覽、勾選與明確確認決定，標題不增加上傳範圍。
3. 程式、測試或實際功能變更必須依內容選擇前綴，不得將所有 PR 一律標為 `feature`。
4. 規則無法讀取、格式無法確認或規則互相衝突時，應顯示可理解的原因並停止受影響的 PR 建立，不得靜默使用英文或疊加狀態標籤。
5. 此要求沿用原有 repo 目標、可見性、上傳預覽與批准邊界；不新增 API、資料庫欄位、模型、技能、權限或自動合併功能。

## 驗收條件 AC-WB-016

- Agent 建立 PR，以及工作台同步已確認專案紀錄所建立的 PR，均使用單一允許前綴與正體中文摘要。
- 同步純紀錄時類型為 `docs`；必要專案名稱可保留原文，其他摘要維持中文。
- 不得產生固定英文標題或 `feature: fix: ...`、`[WIP][QA] ...` 等多重標記。
- 規則缺失或衝突時有明確提示，不以隱藏 fallback 繼續建立 PR。
- 原有明確批准、聊天選項、project isolation 與 PR base/head 邊界保持有效。
